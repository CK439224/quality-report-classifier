# Data

## `sample_reports.csv` (bundled)

A synthetic dataset generated by `generate_sample_data.py` (in this folder), built from templates: a symptom phrase bank per category, randomized mileage/timing/severity details, and some sentence-order shuffling to avoid every row in a category looking identical. It's meant only to let the pipeline run end-to-end with zero setup — see the "Honest limitations" section in the top-level README before reading anything into the resulting metrics.

Columns: `report_id`, `category`, `narrative`.

To regenerate it (e.g. with a different size or random seed):

```bash
python data/generate_sample_data.py --n-per-category 60 --seed 42 --out data/sample_reports.csv
```

## Real data via `src/fetch_data.py`

NHTSA publishes a free complaints API — no key required:

```
GET https://api.nhtsa.gov/complaints/complaintsByVehicle?make={make}&model={model}&modelYear={year}
```

It returns JSON with a `results` array (the live API's exact key casing has changed across NHTSA's API versions — `fetch_data.py` checks a few possible casings defensively). Each result includes, among other fields, a free-text narrative and a component/category string. Relevant fields `fetch_data.py` looks for (again, checked case-insensitively since documentation is inconsistent about casing):

- `summary` — the free-text complaint narrative (this is the "quality report" text)
- `components` / `component` — the vehicle system involved, used as the category label
- `odiNumber` — unique complaint ID
- `crash`, `fire`, `numberOfInjuries`, `numberOfDeaths` — severity indicators, not used by the current models but worth exploring if you extend this into severity prediction

**Before trusting a large pull:** run `fetch_data.py` with `--limit 5` first and open the output CSV to confirm the columns look right for the current API. NHTSA's API has changed shape before and could again; the script prints a warning and dumps the raw first response to `data/_debug_raw_response.json` if it can't find the fields it expects, so you can see what actually came back and adjust `fetch_data.py` accordingly.

Because this project's field labels are automotive `Component` values rather than a real internal quality taxonomy, consider relabeling a subset into categories that mean more for your use case (e.g. collapsing `TIRES`, `WHEELS` into one `TIRES/WHEELS` class) before training, and documenting that relabeling decision — that kind of judgment call is exactly the sort of thing worth writing up.

## Using your own quality data instead

If you have access to real (appropriately anonymized/authorized) NCR, CAPA, or complaint text, the cleanest path is to export it to a CSV with the same two columns the rest of the pipeline expects — `category` and `narrative` — and point the scripts at it with `--data path/to/your.csv`. That's the version of this project that would be most compelling in an interview, since you'd be able to speak to real labeling decisions and real data-quality problems (missing narratives, inconsistent category usage, etc.) rather than a public proxy dataset.
